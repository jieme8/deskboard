## 菜单栏图标不显示（2026-10-21 查清并修好）

**症状**：App 在跑、桌面三块组件都正常，但菜单栏里没有 DeskBoard 的加油机图标。
**日志会骗人**：`NSStatusItem.isVisible` 照样返回 1，App 自己的日志也照打「菜单栏项 可见=1」。

**真凶在系统那边，不在代码里**：macOS 按 bundle id 记账。同一个 id 出现第二份副本时
（构建暂存目录、开发产物、旧版本、装到别处的副本），系统会把旧的那份自动搬进
`~/.Trash/DeskBoard HH.MM.SS.app`，**并且继续留着它的登记**。本机曾攒到 **152 条**同 id 登记，
于是系统认不出「这个菜单栏项属于哪个 App」，整个不画。

三条对照实验把因果链钉死了：

| 实验 | 结果 |
| --- | --- |
| 同一份二进制，只换 bundle id | 图标立刻出现（`整机` 口径无关） |
| 同一份二进制，同一个 id | 不出现 |
| 同 id 但把副本**文件删掉**（登记成死记录） | 仍然不出现 —— 死登记也算数 |
| `lsregister -u` 注销重复路径 | 有效，但被系统重新扫描时又会被加回来 |

**修法（三处，缺一不可）**：

1. **换 bundle id**：`com.hujie.deskboard` → `com.hujie.deskboard.widget`。
   老 id 名下的登记再也和运行中的 App 无关。**配置域跟着变**，所以启动时把老域的值
   一次性搬过来（`migrateLegacyDefaults`，13 项）。
   ⚠️ 搬值要用 **CFPreferences 的原始 plist 键名**（`DeskBoardPlaces` 这种，
   `K()` 已经带了 App 名前缀）。用 `NSUserDefaults` 风格的键名去 `CFPreferencesCopyAppValue`
   会全是 nil —— 踩过。
2. **安装改成原地替换**：只清 `Contents`、保留 bundle 目录本身。
   同 id 换路径会被系统当成「装了新版本」，旧副本进垃圾桶并继续登记 —— 这就是那 152 条的来源。
3. **暂存副本和开发产物各用各的 id**（`.staging` / `.dev`），绝不和生产 id 撞车。

**自检**：`tools/ls_list.py <bundle id>` 列出该 id 名下的登记（按记录块解析，
`lsregister -dump` 的 `path:` 和 `identifier:` 要配对读，只认 `path:` 会把别的 App 算进来）；
`tools/fix_statusbar.sh` 清掉重复登记并把安装副本登记成「正主」。
**判据不是肉眼看截图**：`tools/menubar_scan.py` 做菜单栏逐列墨迹扫描，
跑之前/之后各截一张做差分 —— 新出现的墨迹簇就是新增的图标，位置可量。

## 读数怎么读（活动监视器）

**榜头和每行同一把尺，两边都是「占整机」，满值 100%**：

| 象限 | 榜头 | 每行 | 怎么读 |
| --- | --- | --- | --- |
| CPU | 「整机 37%」 | `1.7%` | 榜头和每行都是 **10 秒窗口**（标题写 `CPU 10s`）：榜头 = 整台机器最近 10 秒的滚动平均；每行 = 该进程占**整机**的百分比（单核百分点 ÷ 核数）。原来榜头印「全核 444%」（12 核满值 1200%），人读不出上限，才改成现在这套。 |
| 内存 | 「16.4/24 GiB」 | `926M` | 榜头是整机已用/总量，行内是该进程驻扎内存；行数只列前四，合计不等于榜头。整列都是 **1024³ 的 GiB/MiB**（标题写 `内存 GiB`），和关于本机、原生活动监视器同一进制。 |

**卡片和活动监视器显示同一拍快照**：系统指标每 10 秒采一次，采完同时推给两块面板；
活动监视器的进程榜也是 10 秒一采。所以两块屏上的 CPU/内存读数不会各显示各的时刻。
CPU 窗口未满（刚启动前 10 秒）时印 `—`，不拿不足 10 秒的差值冒充 10 秒。
| 能耗 | 「前4名占全部 69%」 | `35%` | 分母是**全部可读进程的实测能耗合计**（内核 `ri_energy_nj` 差分，瓦）：行内 = 该进程占它的份额，榜头 = 前四名合计的份额。分母写在榜头上，不再是一个光秃秃的百分数。 |
| 网络 | 「系统 ↓1.2M ↑340K」 | `↓17K ↑262K` | 榜头 = 整机收发速率；每行 = 该进程当前收发速率（`nettop -L 1` 单次采样，累计字节按拍求差）。只覆盖当前用户可读进程；连接数在悬停气泡的 pid 行。 |

**跟原生活动监视器对数时**：那边的每进程 CPU 是「占一个核」的口径（31.9% 就是 31.9% 个核），
这里每行是「占整机」。所以本组件的行内数会小一个核数倍 —— 悬停气泡里两个都给了：
`1.7%（单核 20.2%）`。

**每行三列**：进程 / 现在 / 12h。现在只有一根行底 2.5pt 进度条；12h 是右侧文字列
（CPU/内存/能耗 = 12h 平均，网络 = 该进程 12h 累计字节）。没有记录印「—」，不印假 0。

**卡片的状态档位（2026-10-24）**：每行标签后有一个状态词——温度/磁盘是 正常/偏高/过高（磁盘过高写「将满」），网络/IPv4 是 在线/离线，表尾电池是 正常/偏低/低。颜色青 = 正常、琥珀 = 偏高、红 = 过高/离线。**温度行是 CPU / SSD 两支温度计**（2026-10-29 起），各自按自己的温度上色，热的那颗当主读数；磁盘的行底条底分三段，刻度就是阈值。温度取更热的那个只是状态词和档位的口径；阈值：温度 <70°C 正常 / 70–85 偏高 / >85 过高；磁盘已用 <80% / 80–90% / >90%；电池交流电或 >20% 正常 / 10–20% 偏低 / <10% 低；网络有接口、IPv4 有地址算在线。

**磁盘主读数（2026-10-25）**：不动卡片尺寸/行高/其他行，只把磁盘行数值改成混合字号——「剩 277G」13.5pt 是卡上最大的数据读数，`44% 已用 · 494G` 7.5pt 退成副读数；磁盘条从 2pt 加到 3.5pt。这样容量在现有版面里更重，但不加环、不换行、不加高。（温度行后来在 2026-10-29 换成两支温度计，底条只剩磁盘这一根。）

**卡片文字清晰度（2026-11-09）**：HUD/Bare 档原来在 `drawRect` 开头给整块设 5pt 全局柔影，7–11pt 的文字和药丸/电平条/瓷砖一起被糊成一团；现在阴影只挂到**文字属性**上（`NSShadowAttributeName`），收紧到 **2pt 紧影**（黑 0.90），形状不再投影。同时标签 10→10.5、值 11→11.5、温度名 7→7.5、表尾 8.5/9→9/9.5、电池状态词 7.5→8；磁盘副读数/单位因为加大后会和「正常」药丸挤在一起，保持 7.5/8.5 只提亮；标签颜色从 `VaultMuted` 提到 paper 0.82，磁盘副读数/表尾提亮到 0.72/0.75。卡尺寸、行高、条子和表尾高度都不变。

**卡片的动效（2026-10-24）**：到点时芯片闪一下；值真的变了的行才播水位/数值闪，**跨档（正常→偏高）也算变了，用新档位的颜色闪一下**；网络有流量时行首灯闪 3 下。温度变化 <0.5°C、磁盘 <1% 时水位直接跳到新位置（数字照常更新）；温度计和磁盘条 0.45s ease-out cubic，磁盘比温度晚 40ms；闪烁 0.28s、芯片 0.25s、采样钟闪 0.30s、网口灯 0.5s（晚 60ms 开始）；60fps 表只开约 0.56s，结束即 park。采样钟仍是 1Hz 的常驻成本。变形、隐藏、离屏素材不逐帧。

扫描带和流量点没有恢复：它们不承载数值，是「看不懂」的来源；现在看哪行的状态词/颜色/条子落在哪一段，就知道该值在哪一档。

成本实测：离线基准单帧绘制约 0.70ms（到点活跃帧 1.12ms），采样钟 1Hz ≈ 0.07% 单核，到点动效按 0.56s/10s 摊薄 ≈ 0.38%，合计 ≈ 0.45%，和上一版量级一致。四帧离线预览只证明渲染和时序；真机上的节奏/亮度还要人看一眼。实机 `sample` 受卡片是否被窗口盖住影响（AppKit 不画被遮挡窗口），所以这里用离线基准。这台机器系统里的「减弱动态效果」是开着的；项目里弹药库/活动监视器的动画都没接这个开关，卡片先保持一致（代码里没有拦截），要接的话在 `panel_view.m` 的 `setModel:` 里给 `animate` 条件加一条即可。

四块组件各自记住自己在每块屏每个分辨率下的位置（卡片 / 弹药库 / 活动监视器还各记四角形变），互不干扰。出厂摆位是**系统状态右上、活动监视器右下、弹药库左下、签到中心左上**，统一 16pt 边距；布局版本升到 v2 时会把老存档里三块系统组件的位置一次性迁到新默认，签到中心的档位在首次启动时单独种下，之后用户再拖就由存档接管。菜单里每块都有「恢复默认位置」。**分辨率真的变化时会立刻按当前这套角 + 边距落到新档位**，并把同一块屏的旧档位同步成这个摆位，不再沿用旧分辨率的布局；只是显示配置抖动、点尺寸没变时只重申位置。四块组件都固定贴在桌面图标层，任何模式下都不会浮到应用窗口上面（全屏窗口也不例外）——层级是硬约束，菜单里没有开关能改它。

四块都是**整块可拖**：卡片面板连变形留白一起算抓取区，弹药库的空白处和普通卡片拖动都会移动组件（⌥+拖卡片仍是拖出库），活动监视器和签到中心按在任意非热点处都能拖；只有按钮/抛掷点这类热点保留原动作。菜单栏「锁定位置」是四块共用的唯一锁：**上锁时立刻把当前摆位写进各自存档**（卡片会顺手提交「待保存」），四块都不再响应拖动、菜单里的搬位动作也会被拒；解锁后才能继续调整。调整完再上锁，新位置就是下次启动/换分辨率回到的地方（「恢复默认位置」仍回出厂四角）。锁态存在 `LayoutLocked`，重启保持。

弹药库的玻璃底板不是一张固定图片，而是每次从**用户真实的桌面壁纸**上采样组件背后那一块、模糊、提饱和后压一层暗角。和卡片面板、活动监视器、签到中心共用同一套 `DeskBackdrop` 采样逻辑，所以换壁纸、挪位置都天然贴合。四档外观共用同一个 `DeskStyle` 枚举：实底卡采样壁纸压成玻璃，羽化暗角不采样只叠暗区，无底浮字和无边玻璃都完全透明——**无边玻璃按用户要求不再垫任何玻璃底雾**（2026-11-07），背后直接透出实时壁纸，只留文字、文字投影和刻度色，不画边框和准星。

## 组件 3：活动监视器（CPU · 内存 · 能耗 · 网络）

四榜并列，每榜 4 个进程（**简略模式 272×142，每榜 1 个**），全部读这台机器的真实数据，零权限、零弹窗。**没有抬头和表尾**（2026-10-29 按用户要求删掉），外观与弹药库同一套：玻璃板、四角准星、带描边瓷砖榜；网络榜的榜头是系统收发速率，行内是每进程 `↓/↑` 速率。

**简略模式（2026-11-09）**：菜单「活动监视器 ▸ 简略模式」勾选，存档键 `MonitorCompact`，默认关。卡片缩到和系统状态卡同尺寸的 **272×142**，外边距 12、格间距 8，四个 **120×55** 格仍按 CPU 左上 / 内存右上 / 能耗左下 / 网络右下铺。每格只留两行：指标名 **9pt** + 榜头总量 **9.5pt**（放不下自动收到 8.5/8），第 1 名进程 **10.5pt Medium** + 现在值 **10.5pt Medium**（值先缩到 8.5pt 再考虑截名字），行底一根 2pt 条；12h 列、列名和格内图标都收起，进程全名和 12h 仍由悬停气泡（240×192）给全。HUD / Bare 档的小字用 **2pt 紧影**而不是完整模式的 7pt 柔影，小字才不会被光晕糊掉。一格里只有一个进程，所以悬停和双击改成**整格**生效，按住拖动仍在整块任意处（双击除外）。
简略模式的条长换了尺：完整模式是「相对本榜前 4 名峰值」，只剩一行时那样会让每根条都顶满；简略改成**占该格榜头分母的份额** —— CPU 占整机、内存占物理内存、能耗占全部可读进程、网络占系统总速率，非零最小画 3pt，未知或分母 ≤ 0 只留槽。切换模式会重建监视器窗口，摆位存档的「角 + 16pt」不动（右下角缩小不漂）；四角位移是点偏移，切换时按新卡片尺寸重新夹紧，若在调角模式会先退出。采样仍是 10 秒一拍，进程榜照常排前 4、12h 照常算好，只是少画 12 行，切回完整模式不会出现 12h 空窗。

- **口径**：每进程 CPU 走 `proc_pid_rusage` 的 user+system 时间两拍求差（rusage 给的是 mach 刻度，
  本机 1 刻度 = 41.667ns，忘了换算 %CPU 会少算 41.7 倍 —— `verify.m` 里"烧一核自报 99.9%"
  那条断言就是守这个），两拍间隔就是 10 秒；榜头的整机 CPU 是 `host_cpu_load_info` 的
  **10 秒滚动窗口**（10 秒一采，用目标时刻两侧两拍 tick 插值到正好 10 秒），所以榜头和行内窗口一致。
  整机内存已用走**原生活动监视器口径**（匿名内存 − 可清除 + wired + compressed），
  不是 `active + wired + compressed`（后者漏掉不活跃的匿名页，本机实测少算约 1GB）；每进程内存是
  `ri_resident_size`，整块板子统一 1024³ 的 GiB/MiB。能耗取内核 `ri_energy_nj` 的纳焦差分
  （换算成瓦），榜头仍印**占全部可读进程的份额**；原生活动监视器的"能耗影响"是另一套加权分，
  绝对数不可比，但本机实测两者排名一致（DeskBoard 0.34W 排第一，UURemoteServer 每秒 1000+
  次唤醒却只有 0.014W）。只有内核不给计数时才退回 CPU 时间 + 唤醒次数加权，保证榜不空。
  网络这一榜是**每进程收发速率**：`nettop -P -x -L 1 -J bytes_in,bytes_out` 单次日志采样
  实测约 0.01s，输出累计字节，组件每 15 秒起一次进程、按拍求差（中间几拍沿用上一次速率，
  历史按 dt 加权，不会把 15 秒的字节数当 5 秒重复放大）。烧 146% 单核的是持续交互模式，
  不是这种一次性采样；NetworkStatistics 的 NStat* 符号在当前系统上已经 dlsym 不到，不走私有 API。
- **单位规则（这块板子被吐槽过三轮，规矩就四条）**：
  ① 榜头和榜内必须同一把尺 —— CPU 这条尺换过两次：最早榜头印"整机 11%"而每行是"占一核 20.2%"，
  两个分母并排放着，人第一反应就是"总数怎么比单个进程还小"；改成"全部核加起来"（12 核满载 1200%）
  之后又被撞了一次："173% 是什么？CPU 总量不是应该 100% 吗"。**现在榜头和每行统一成「占整机」**
  （满值 100%），榜头写"整机 37%"，每行写占整机的百分比，"总 ≥ 任意一行"由构造保证，
  而且每个数都跑不掉 0~100。
     但"同一把尺"**不等于**"榜头必须是每行之和"：内存榜头是**整机已用 / 物理总量**，不是每行 RSS
     之和（共享内存会让行和超过物理量，而且那里真正有用的数就是整机水位）。这条规矩管的是
  "别让人误以为榜头是聚合、拿去跟单行比大小"，不是"必须是聚合"。
  ② 自造单位的绝对值不许上屏 —— 能耗每行原来印"191"，那是 `CPU% + 唤醒×0.08` 的裸分，
  没有任何人解读得出来；现在底层换成内核实测瓦数，每行印**占全部可读进程能耗的比例**，
  榜头印"前4名占全部 xx%"，两者共用同一个分母 `energyShareTotal`（同一次循环算出来的，
  不留第二套真相）。
  **分母必须写在脸上**：光一个"66%"没人知道是占谁的，所以榜头明写"占全部"。
  ③ 数字一律带单位 —— 每行 CPU 现在印 "1.7%"（占整机），不再是裸的 "20.2"。
  分母为 0 时印 "—" 或 "0%"，绝不印 `nan%`（`verify.m` 有专门一条守这个）。
  ⑤ **哨兵值不许印成数字** —— `procs.m` 用 `-1` 表示"这一拍还没有上一拍可比"，
  照着印百分比会得到 "-1.0%"（实测在悬停气泡里出现过）。未知就是未知，印"—"。
  ④ 小到看不见的数不许印成假 0 —— 换成占整机后数值会变小（0.04% 会被四舍五入成 "0.0%"），
  真 idle 的进程和"小到看不见"在屏上长得一样，所以印 "<0.1%"。
- **可读性重排（2026-10-22）**：监视器从 432×294 放大到 **560×380**，四榜仍是 2×2；
  每行从「名字 + 值 + 两根条」改成「进程 / 现在 / 12h」三列，只画一根 2.5pt 的现在条。
  12h 不再用淡条（用户反馈第二根线看不懂），改成文字列：CPU/内存/能耗是 12h 平均，
  网络是该进程 12h 累计字节；没有记录印「—」。名字 10.5pt、现在 10.5pt、12h 13pt Medium，
  行高 24pt；12h 列的数字和列名直接落在卡片玻璃上，不再铺深色小底（用户明确要求去掉）；
  HUD/Bare 档靠原有的文字阴影保可读性；底部图例也提亮。
  底部状态条保留「榜内 12h 累计」总览，网络行和它不要求相等（总览按已跟踪进程求和）。
- **去掉抬头和表尾（2026-10-29）**：抬头（芯片 + 「活动监视器」+ `ACTIVITY MONITOR · PROC-01 · N`）
  和底部图例（「条=现在 · 右列=12h … · 行=可读进程」、「榜内 12h 累计 … · 共 N 条连接 · HH:mm 采样」）
  整块删掉，卡高 380 → **330**：上下各留 14pt，四榜的格子高度、行高、条子位置全部和删之前一样，
  只是卡矮了 50pt。只喂表尾的三处计算（12h 网络总览、socket 求和、`procCount`）一并删掉，
  10 秒那一拍少走一次全进程求和。`verify.m` 改成守「它们没有偷偷回来」。
- **覆盖范围**：只列当前用户可读的进程（实测 542 可读 / 274 被拒，WindowServer 这类 root 进程读不到，
  `top` 能看到是因为它 setuid root），所以网络榜的行和与榜头系统总量本来就不要求相等。
- **单条进度**：只画一根行底 2.5pt 条，12h 用文字列；删掉第二根条后行内不再有两条基线抢空间。
  重绘仍只在 10 秒一拍和悬停变化时发生。条子不再做逐帧缓动：每拍直接落到目标长度，
  少掉整卡 60fps 重画，这是把常态 CPU 从 5% 降到 1% 上下的主要一步。
- **刷新**：进程榜 10 秒一采；榜头的整机总量跟着卡片每 10 秒系统采样一起推过来，
  两块屏永远显示同一拍。动画表空闲即停，组件自己标脏才叫回来。
  实测整个 App 稳态约 1.1% CPU（10 秒一拍、条子直接落位；被应用窗口盖住时更低）。
- **调角模式**：和卡片面板、弹药库同一条路 —— 先画正的烘成位图，再按四角投影。未变形时走
  实时绘制，所以文字是原生清晰度，只有拖角看形状时才付位图的清晰度代价。变形态整条悬停关掉
  （命中测试还在未变形坐标上，斜着放会点错行），窗影也关掉（外框是矩形，窗影会出卖它）。
  重烘只在换拍 / 改角 / 改外观 / 挪窗时发生，不跟缓动逐帧烘。

## 组件 4：签到中心（CREDITS）

**小字清晰度（2026-11-09）**：签到没有整块阴影问题，真因是大量 **6–7pt** 的小字又偏灰。计划副行 6.7→7.4、记录行 6.2/8.8/6.0/6.2→7.0/9.2/6.8/7.0、状态 9→9.5、最近签到 7.2→7.8、页脚 7.2→8.0、药丸 7→7.5、平台名 10→10.5；副标签从 `VaultMuted` 提到 paper 0.68–0.78，主余额 22pt 和统计色不动。记录行整体上移 1pt，给抬高后的字让位；槽尺寸、记录尺和药丸位置都没变。

### 90 天总积分纪录 + 最近签到（2026-11-07）

每个平台独立记录自己的**总积分（余额）**在最近 90 个北京时间自然日里的最高值，四项不相加、不排名。槽内新增两处只读信息：

- **状态行右侧**：`最近签到 11/7` / `最近领取 11/7`，是该平台最后一次成功签到/领取的日期。失败不更新；幂等的「已签」按成功算；日期不受 90 天窗口裁剪，超过 90 天仍保留；授权/错误态隐藏，完整日期和金额在悬停详情里。
- **记录行**：`90天最高 16,200 积分 · 9/14`（不足 90 天写 `63天最高`，未知写 `—`）。下面是 **90 天记录尺**：全宽轨道 + 只画有采样的短柱，一格一天，空缺=那天没采到，亮格=峰值日，琥珀=今天；峰值日等于最近签到日时不重复写日期。它替代原来的 1pt 分隔线。未接入槽不画记录行、记录尺和最近签到。
- **新高**：当前余额超过窗口峰值时值/日期转青色并带小三角，日期写「今天」；并列最高保留最早那天；旧峰值滚出 90 天后自然回落到窗口内最高，不播新高。

数据在 `~/Library/Application Support/DeskBoard/Credits/records.json`（0600，原子写 + `.bak`），只在每次余额同步时按日取最大，不联网、不回填、不保存 token；能拿到 uid 的平台按账号分档，换号时该平台的记录和最近签到一起重置。`verify_credits` 覆盖 90 天窗口、峰值、覆盖、并列、滚出、换号、最近签到、新高、未接入隐藏；`preview_credits` 出四槽图。

**Qoder 药丸颜色（2026-11-08）**：药丸回答“今天还要不要签”，不跟当前窗口的 `claimed` 走。Qoder 窗口是 10:00→次日 10:00；早上 10:00 前窗口仍属于昨天，状态会显示本窗口已领，但当天还没签，药丸保持待签黄；10:00 后领取成功、最近签到变成今天才转青。底栏按窗口结束日写「今日/明日 10:00 刷新」。

**组件内授权**：MiniMax 未授权 / 登录过期时，MiniMax 槽的状态词直接写「未授权 · 点此授权」/「登录过期 · 点此授权」，**单击这一格就发起浏览器授权**（和菜单「重新授权…」同一条路）；单击已授权槽是刷新，双击是立即签到。Trae 未登录 / 令牌过期时写「未找到登录态 / 登录过期 · 点此打开」，单击打开 Trae 客户端；已连接时单击刷新、双击立即签到。Qoder 的 PT 缺失 / 失效时，单击写「未设置 PT · 点此设置」/「PT 失效 · 点此更换」并弹出令牌输入框；已连接时单击刷新额度与活动、双击立即领取。WorkBuddy 未登录 / 登录过期时单击直接发起浏览器登录；已连接时单击刷新、双击立即签到。**每格右上角的药丸就是手动签到按钮**：已签 / 待签都写「签到」，需要授权写「授权 / 打开 / 登录 / 设置」，失败写「重试」；点它只签这一格（已签时是幂等补签），点格子正文仍是刷新。

**悬停**：每格悬停给自己的详情——MiniMax 是 7 天逐日积分、免费/购买拆分、套餐和上次同步；Trae 是登录态到期日、不自动续期说明；WorkBuddy 是积分可用/已用/总计、今日状态、连签天数和登录到期日；Qoder 是额度可用/已用/总计、本窗口待领或已领、窗口起止时间和上次同步。主条不堆字。

**菜单**：`签到中心 CREDITS（n/4 已接入）` 下四个同级子菜单，每个平台各有自己的「立即签到 / 领取」；MiniMax 用「重新授权…（浏览器 OAuth）」，Trae 是「从本机重新读取登录态」，WorkBuddy 是「登录（浏览器）… / 立即签到 / 刷新额度 / 从本机导入明文登录态 / 打开 WorkBuddy」，Qoder 是「设置 / 更换 PT 令牌…」和「打开 Qoder 用量页」。另有「立即签到（全部平台）」一键手动跑满四格、「立即检查（补签）」立即刷新并补签（手动不受 10:05 时间门限约束）；没有跨平台积分合计——积分和 Credits 不是同一把尺。

**WorkBuddy 接入**：5.6.2 起客户端把 `workbuddy-desktop.info` 的 token 包成 `$wbEncrypted` 信封，at-rest key 只驻留客户端内存，硬盘上没有可复刻的明文；所以走桌面端同款官方浏览器授权：`POST /v2/plugin/auth/state?platform=WorkBuddy` → 浏览器登录 → `GET /v2/plugin/auth/token` 轮询拿 token；再 `checkin-activity-status` / `daily-checkin` / `get-user-resource`。token 存在 `~/Library/Application Support/DeskBoard/Credits/workbuddy.json`（0600），到期前用 refreshToken 自动续期（这是我们自己的浏览器会话，不会轮换客户端那份 refreshToken）。老版本客户端或自己导出的明文 `auth.info` 仍可用菜单「从本机导入明文登录态」只读导入。首次实测：`2026-10-27 13:39:26 签到 WorkBuddy 自动签到` → `签到成功：+100（连签 27 天）`，余额 2,847 → 2,947，令牌到期 2026-11-26。

**Qoder 接入**：PT（`pt-…`）先 `POST /api/v1/jobToken/exchange` 换成 24h 的 job token，再 `GET /api/v1/userinfo`、`GET /api/v2/quota/usage`、`GET /sash/api/v1/me/campaigns?clientType=10`；活动 `CLAIMABLE` 时 `POST /sash/api/v1/me/campaigns/{id}/claim`（幂等）。PT 只存在 `~/Library/Application Support/DeskBoard/Credits/qoder.json`（0600），从不读写 Qoder 客户端目录，也不打印到日志。活动窗口是北京时间每天 10:00 到次日 10:00；统一在 10:05 后自动领，之后每小时 :05 检查一次，窗口内发现可领就补签，失败一天最多重试 3 次、间隔 30 分钟。首次实测：`2026-10-27 10:40:40 签到 Qoder 领取成功：+100 Credits`，余额 2,033 → 2,133。

**自动领取**：四个平台统一在北京时间每天 **10:05** 后第一次有机会就查 status，未签才 claim；之后每小时 :05 再检查一次，没签就补签；电脑睡眠就等唤醒补领。手动入口是每格右上角的药丸（单平台）和菜单「立即签到（全部平台）」，手动不受 10:05 门限限制。MiniMax 的历史无人值守实测：`2026-10-27 00:05:39 签到成功：+400`；新策略下 10:05 档位由 `verify_credits` 的时间断言覆盖。授权续期用 provider 自己的 OAuth 链，绝不读写 MiniMax Code 桌面客户端的 `~/.minimax`。

**数据与工具**：凭据和快照在 `~/Library/Application Support/DeskBoard/Credits/`，`auth.json` 权限 0600；`tools/try_credits` 提供 `authorize / status / balance / claim --yes / json / selftest`，Trae 走 `try_credits trae <status|balance|claim --yes|reload|json|path>`，Qoder 走 `try_credits qoder <status|claim --yes|json|path|token <pt>>`，WorkBuddy 走 `try_credits workbuddy <status|claim --yes|json|import|login|path>`（从不打印 token，设备号只报位数）；`tools/preview_credits` 出四槽离线图；`build.sh --check` 会跑 `verify_credits` 的全部断言。窗口校验 `dump_window` 现在按宽度识别 700×132 的签到中心。

**外观**：四档 `DeskStyle` 都支持；每块槽自己带深色玻璃底，所以羽化 / 无底 / 无边玻璃在亮壁纸上也能读。周条缩成 7 个轮次点留在主条，逐日数字放悬停。

## 12 小时历史（活动监视器）

每行进程现在画一根 2.5pt 条（现在）+ 右侧 12h 文字列：CPU/内存/能耗是 12h 平均，
网络是该进程 12h 累计字节。精确的 12h 数字在悬停浮层里。

网络榜每行第三列就是 **该进程的 12h 累计流量**（收发合计，字节）；底部状态条另外给
**榜内 12h 累计**（按已跟踪进程求和，和可见的 4 行不要求相等）。悬停某个进程时，气泡底行
也显示该进程自己的 12h 累计。用进程累计而不是网卡计数器累计，是因为后者回绕时会产生
1e20 量级的脏桶，把 12h 总和带飞；实时那行仍是系统网卡速率。没有历史就印「—」，不印假的 `0B`。

为什么要自己攒：macOS 没有任何公开 API 能给"过去 12 小时"的任意指标 —— `getloadavg` 只到
15 分钟，`host_cpu_load_info` 和网卡计数都是"自开机累计"，而开机几天是常态，since-boot ≠ 12h。
所以 `DeskHistory` 把每 5 秒那一拍按分钟攒成桶，落盘在 `Application Support/DeskBoard/History-12h.plist`。

三个口径决定，都是实测后定的：

- **分母 = min(窗口, 窗口内真正攒到的秒数)**，不是写死的 43200。写死的话冷启动头一天分子只有
  几分钟、分母却是 12 小时，任何进程的 12h 条都是亚像素长度 —— 等于装好之后一整天看不到这个
  功能。用 min 之后攒满 12 小时自动收敛回字面口径，没攒满时是"已记录这段时间的平均"，界面拿
  `covered` 标"已记录 X 小时"，两个阶段都不撒谎（两条都有断言）。
- **只跟踪四榜前 6 的并集**（封顶 40 个 pid），不存全部 542 个进程。取前 6 而不是前 4 是给榜
  留滞后余量：一个进程从第 5 名掉出去时这一小时的平均还在，不会画着画着突然变 0。
- **只列当前活着的进程**，历史只作为它的一列。12h 榜上出现已经退出的进程会和"实时监视器"自相矛盾。
- **隐藏时继续采**：否则"隐藏 6 小时"会在历史里留 6 小时的洞，而分母按窗口算会把洞当成 0，
  恢复显示后数字长期偏低且看不出来。

两个实测教训：`leaders()` 一开始写成"四个指标各 sort 一遍 542 个进程"，整个 App 从 2.9% 顶到
**8.5% CPU**，改成一趟扫描 + 四个定长小数组才回到 3.4%；plist 读回来的桶是**不可变**容器，浅
`mutableCopy` 之后下一拍追加会撞 `-[__NSArrayI setObject:atIndexedSubscript:]`，而且只有"重启后
正好又采到同一 pid 的同一分钟"才炸 —— 表现为偶发 SIGABRT。

## 组件"点不动 / 拖不动"的排查顺序

**2026-10-20 已量到并修掉的根因：位置存档的边距下限把贴边拖动夹回原位。**
`saveMonitorPlaceInWindow:` 原先把 dx/dy 夹在 `[16, 屏宽-卡宽-16]`，而活动监视器正贴在
dx=dy=16 的下限上。于是任何朝上/朝右的拖动在落档时被夹回 16，而"屏幕参数变更 → 只重申位置"
在这台机器上每几十秒就来一次，窗口就被搬回原位 —— 用户看到的就是"按住拖了又自己弹回来 = 拖不动"。
下面那批候选（遮挡量级、跟踪区选项、调角 return）都是在它后面兜圈子的东西。

结论靠**活体自检**拿到，不依赖真鼠标，也不受遮挡影响（它走的是生产代码路径，测的是真窗口）。三档：

```bash
# 注意：必须直接拉二进制，`open` 不会把环境变量传进去
DESKBOARD_SELFTEST=1 /Users/hujie/Applications/DeskBoard.app/Contents/MacOS/DeskBoard
#   方向七发：四个方向 + 三发跨屏幕中线（corner 换边是历史事故区）
#   每发报「拖后位移 / 重申后位移 / 零漂 / 判定」，判定分三种：
#     守住 = 停在松手处；夹到可视边界 = 合法停住（不是 bug）；弹回原位 = 真 bug
DESKBOARD_SELFTEST=2 …   # 按点扫描 14 个按压点（榜头/行文字/左右留白/四角），报「起拖 / 搬窗」→ 查死区
DESKBOARD_SELFTEST=3 …   # 菜单「微调」走位：左 12 次 + 上 6 次，核对位移与重申后是否守住
DESKBOARD_SELFTEST=4 …   # 九宫格摆位：九个落点逐个核对期望/实测，跑完还原原档位
```

两条仪表纪律：跑完**自动还原存档**（零副作用，别把自检当成摆位）；合成事件期间**视图日志静音**
（否则「按下」计数会被灌满 —— 实测 0→37→44，而那条正是 `tools/diagnose_drag.py` 数真人信号的口径）。
菜单里也有同一入口：活动监视器 › 自检：模拟拖 30pt（不用真鼠标）。

同一份代码的改前/改后对照（这就是负向对照）：

| 方向 | 改前重申后 | 改后重申后 |
| --- | --- | --- |
| 右上（超边距）+30,+30 | **+0,+0 被拉回** | +30,+30 守住 |
| 左下 / 右上(边距内) / 正下 60 | 守住 | 守住 |

存档下限改成 0（只保证整块留在可视区）之后四个方向全守住。副作用：组件可以贴边停放；
「摆到四角」仍沿用现有 dx/dy 档位，不受影响。

**被普通层窗口压住时怎么办 —— 用户已定：保持现状，靠菜单摆位。**
这台机器上桌面层组件常年被 Qoder / MiniMax Code / DBX / 访达 的 layer=0 窗口 100% 压住（实测多次），，
按住拖是拖不动的，这不是 bug。**可点占比量过一次**：连续 80 秒 / 40 次采样，40 次全被压住 = **0% 可点**
（另一时刻 10:54 曾短暂露着，所以不是"永远"，但正常干活时几乎永远压着）。用户明确不要「被盖住自动收起」（弹药库那套）、不要「抬到普通窗口之上」、
也不要「临时抬起 10 秒给你拖」。**以后别再给监视器加遮挡保护**，要摆位就用菜单
「活动监视器 › 摆到（不用按住拖）」/「九宫格摆位（不用按住拖）」/「微调 20pt（不用按住拖）」。
九宫格给九个落点（上中下 × 左中右，边距 16pt、中间居中），一次到位 —— 原来只能 20pt 一格格挪，
从右上角挪到屏幕中间要点二十多下。实测九个落点全部精确到位（`DESKBOARD_SELFTEST=4`，0 偏），
菜单微调走位也可靠（`=3`：左 12 次 = −240pt 与期望一致，向上止于合法顶界 +16pt，重申后守住）。

**核对读数别用区域截图**：组件被普通层窗口压住时，`screencapture -R` 拍到的是压它的那个窗口。
逐窗抓才看得见组件本体 —— `probe_clickcatcher 监视器` 现在会顺手打窗口号：

```bash
id=$(./build/tools/probe_clickcatcher 监视器 | grep -o "窗口号 [0-9]*" | grep -o "[0-9]*")
screencapture -o -x -l$id /tmp/w.png        # 绕过一切遮挡，拿到组件自己的像素
```

坑：逐窗抓出来带 alpha（非透明窗），近白的数值叠在白底上会"看不见"，看着像渲染缺陷 —— 那是
合成的假象。要按代码里量过的壁纸亮度（监视器底下 p95=44）把图 alpha 合成到暗底上再看，
实测数值区对比 5.3 倍（底 46 / 字 248），是清楚的。

**先查遮挡，再改代码** —— 三块组件都在 `kCGDesktopIconWindowLevel`（桌面图标层），
任何一个全屏窗口（远程桌面、投屏、某些截图/会议软件的覆盖层）压在它上面时，鼠标事件
根本送不到组件，这时候改拖拽代码是白改。一条命令就能分清：

```
./build/tools/probe_occlusion
```

它只把 **layer 0~1000 的普通窗口**算作遮挡（浏览器、IDE 这类真的吃点击的），
layer 极高的全屏覆盖层（远程桌面 / 投屏 / 会议软件）**单独归类、不算遮挡** —— 因为它真吃点击的话
用户整个桌面都点不动，把它算成遮挡会得出假结论（本机就有这么一个 layer≈INT32 的
`UURemoteServer` 全屏层，第一版把它误判成遮挡，把排查带偏了一整轮）。
同时报"被盖住百分之多少"和"四角 + 四边中点共 8 个抓取点还剩几个空着"，
因为只要有一个抓取点没被压住，用户就能拖。

**但这条命令只能在"拖不动"正在发生的那一刻作数。** 实测过一次：卡片面板和活动监视器同时被
普通窗口 100% 盖住、8 个抓取点全被压住 —— 可当时整屏那块区域亮度只有 29，而组件自身内容
平均 65，说明组件**连看都看不见**。看不见就意味着用户报"拖不动"那会儿肯定不是这个状态，
这条测量只能证明"现在挡着"，不能证明"当时是它挡的"。

所以正确的用法是：**拖不动的当场**跑一次 `probe_occlusion`，别事后跑。

**还有一类遮挡以前被漏掉：同层的 Finder 桌面图标窗。** 14:47:23 实测到一条
`layer=-2147483603 覆盖100% 访达` **排在活动监视器前面** —— 它和我们同一层，同层之间比排列顺序，
它在前头就会在覆盖区域把点击拿走。`probe_clickcatcher` 现在把"同层且在前"也算成吃点击。**注意：这条改动里"部分遮挡也报比例"那 3 行还没被真实场景跑到过**（构造过 23%/79% 两个矩形，
但桌面状态在两次命令之间就变了，没能复现）—— 别把它当成已验证的行为。

**但这条只见过一次，别把它当结论**：30 秒后再看就没有了；专门做实验确认**不是我的截图招出来的**
（截图前后同层列表都只有我们自己的两块窗）。一个来去匆匆的窗口只能造成**偶发**拖不动，
撑不起"完全拖不动"。它值得留着是因为它偶尔会和组件同层抢位 —— 怀疑撞上它时，
用菜单「摆到」换个角再拖。

**2026-11-09 卡片拖不动的根因：同层访达窗这次是常态，不是偶发。** `probe_clickcatcher 全部`
实测卡片窗排第 19、访达排第 18 且覆盖 100% —— 点击全归访达，`mouseDown` 根本到不了视图。
监视器 / 弹药库 / 签到早就有「定时顶回本层最前」（`raiseMonitorAboveSameLayer` /
`checkVaultCover:` / `raiseCreditsAboveSameLayer`），**卡片是四块里唯一漏掉的一块**，
所以别的都拖得动、只有卡片按住一动不动。修法：四块统一由 `raiseSameLayerTimer:` 每 3s 顶一次
（正按住拖的那块跳过，别从用户手里抢窗；监视器气泡可见时把它再顶回来）；修后同一探针
卡片排到第 16，前方不再有同层访达窗。
**顺带修掉同一类空窗**：监视器原来 30s、签到 60s 才顶一次，16:36 用户报「监视器又不能拖」，
日志里 16:31 之后零条「按下」= 事件没到视图，而稍后探针又显示前方干净 —— 就是桌面窗抢到前面后
等下一次顶回的那几十秒。现在监视器 / 签到也走 3s 这一拍。
这条同时说明「桌面图标那条路已排除」不能一概而论：它取决于哪块窗最近被顶到本层最前。

**先记住一件最朴素的事：这块组件按硬约束永远在你的应用窗口之下**（`kCGDesktopIconWindowLevel`，
不许盖住任何窗口）。所以只要有任何一个窗口压在它那块区域上，点上去到的就是那个窗口，
"拖不动"是必然的、不是 bug。13:59 实测：`MiniMax Code`（layer=0）**100%** 压住活动监视器、
`AI Worker`（layer=3）再压 58% —— 这个状态下它不可能被拖动。判"当时是不是这个原因"，
用 `probe_clickcatcher`（`全部` 或 `rect X Y W H`）在当场量一次即可。
顺手记一句：**桌面图标那条路已排除** —— 实测窗口列表里 Finder 根本没有与监视器同层、
或在它前面的窗口，所以"右上角图标列压住组件"这个想当然的说法不成立。

**一条命令自己看结论**（不用等 AI 读日志）：

```
python3 tools/diagnose_drag.py
```

它只取最近一次启动之后的日志，按 `按下 → 收到拖拽事件 → 拖动中 → 松手 位移` 这条链给判定：
没有按下 = 事件没进来；有按下没拖拽 = 断在投递层；有拖拽没松手 = 中途被打断；
链路完整但总位移≈0 = 被别处按存档重申回去了。三条分支都用合成日志验过，不是只会说"没数据"的摆设。
事后跑出来的遮挡，多半只是"你现在开着别的窗口"。

遮挡排掉之后，再验派发链：`./build/tools/probe_drag` 用
`[NSApplication postEvent:atStart:]` 把事件塞进本进程自己的队列（不碰系统事件流，
所以**不需要辅助功能权限**），跑一遍 run loop 让 AppKit 走完
NSApp → 窗口 → hitTest → 视图 的真实派发，看 `mouseDown/mouseDragged/mouseUp`
三段是不是都送到了视图。局限：`NSEvent.mouseLocation` 取的是真实光标，
"窗口到底位移了多少"测不了，只能测"事件到没到视图"。

**遮挡要用 A/B 判，不能只看"有没有被盖住"。** `probe_occlusion` 报 100% 被盖住，
只说明"此刻有一块窗口压在上面"，不说明"它吃点击"——`kCGWindowLevel` 里 Dock 有一块
layer=20 的全屏窗，任何桌面层组件都被它 100% 压着，但组件照样点得动（那块窗自己不吃鼠标）。
所以判遮挡必须拿**能拖的那块**当对照：

```
./build/tools/probe_clickcatcher 全部
```

它按 `CGWindowListCopyWindowInfo(OnScreenOnly)` 的**从前到后**顺序，对每块组件列出
压在它前面的窗口和各自覆盖率。实测三块组件被同一批窗口（Dock 全屏窗 + 一层
layer≈INT32 的远程桌面覆盖层）以完全相同的方式压着 —— 覆盖率相等就不是差别，
遮挡这条到此证伪，别再往下猜。

活动监视器这里**确实有一个模式陷阱**：`mouseDown:` 里原来写着
`if (_editing) { [self trackCornerDrag:event]; return; }`，一进调角模式整块组件一点都拖不动；
而卡片面板（`panel_view.m`）和弹药库（`vault_view.m`）在同一模式下是先
`DeskQuadHitTest`，**只有命中角点才 return**，没命中就照常拖窗。三块组件现在共用这一条规矩，
`verify.m` 里"开着调角模式按正中间，照样进入拖窗态"和"按在复位角点按钮上不拖窗"两条钉住它。

**时间线才是关键**：`git log -S nextEventMatchingMask -- monitor_view.m` 显示那个 8 秒模态循环
从 0.0.4（10-18 21:42）一直活到 0.0.11（10-19 09:49）才被删，而用户的抱怨是 11:11 提的、
描述的是**之前**的尝试 —— 极可能撞的就是那一版。在那一版里，非 key 的桌面层窗口在 `mouseDown:`
内自开 `nextEventMatchingMask:` 等拖拽事件，应用不活动时事件未必进得来，循环空等 8 秒后超时，
窗口一动不动。**注意别把两件事混了：我做过的是"我的测试抓不到旧写法"（证伪了测试），
从没证明"旧写法在真鼠标下无害"。** 现在两个真 bug 都已修掉（模态循环 09:49、重建风暴 13:44），
你抱怨时那版代码已经不存在了。

**但这条不是用户那一次"拖不动"的已证原因**：`~/Library/Logs/DeskBoard.log` 整份历史里只有
10-17 两条"卡片调角模式"，**没有任何一条活动监视器的调角开关** —— 用户根本没进过那个模式。
所以它是个真 bug（已修），不是他撞的那个。剩下两种可能靠一条日志分开：`mouseDown:` 最顶端
（任何提前 return 之前）打 `按下：调角=? 变形=? 双击=? 窗原点=?`。用户试一次之后，日志里
**有**这行 = 事件送到了视图，问题在算法；**没有** = 事件根本没到，问题在层序或某个吃点击的
窗口 —— 那时候用菜单里的「摆到（不用按住拖）」换角落，不依赖按住组件也能搬。

日志还给出两条硬事实：**双击过监视器**（`10:55 活动监视器 打开活动监视器看 pid 809`，那行只在
`mouseDown:` 的双击分支里）—— 所以事件到得了视图，遮挡/层级一类解释全部出局；**弹药库真拖过 71 次**
（「拖动中 光标… 窗口原点…」逐帧对得上）—— 所以同一套 `VaultDragFrame` + 桌面层窗口在真鼠标下是有效的。
顺着这条把最后一处不对称对齐了：**只有监视器用 `setFrame:display:animate:NO` 挪窗**，卡片用
`setFrameOrigin:`、弹药库用 `setFrame:display:`。但**这条不是已证根因**：负向对照量过，换回
`animate:` 那版 216 条断言一条不动 —— 校验 CLI 里没有真窗口服务器事务，这个差异只有真鼠标能判。
所以监视器也补上了弹药库同款 trace（每 8 帧记「拖动中 光标+窗口原点」、松手记总位移），
一次尝试就能看出断在哪一环。

**已找到并修掉一个真 bug（但它不是"只有监视器拖不动"的原因，见本节末尾）**：`screenDidChange:` 每次都把三块组件的窗口全部销毁重建。
这台机器的显示配置每 8~30 秒抖一次（日志实测 12:43:18/:32/:39/:47/:57、12:46:31/:56 连续多条
「屏幕参数变更，按存档重申位置」，**每条后面都紧跟三行建窗**）。旧写法对每条通知都无条件
`rebuildWindows` + `rebuildVaultWindows` + `rebuildMonitorWindows` —— 用户按住活动监视器拖到
一半，那个视图就被换成新的，`mouseDragged:` 永远送不到。这正好对上前面两条证据：`mouseDown`
到得了（10:55 双击那条），而整份历史没有一条「收到拖拽事件」。附带症状也解释了：活动监视器
每次重建后空板几秒（榜要等下一拍才有数据）。
修法是先比**屏幕配置指纹**（屏数 + 每屏 `displayID`/点尺寸/原点）：真的变了才重建，否则只重申位置。
**实机验证**：新版 12:48:46 又收到一条通知，日志写「配置指纹没变，只重申位置，不重建窗口」，
后面不再跟建窗行。

**现场统计（同一份日志，按启动分段数出来）**：修复后那次启动至今 15 条屏幕通知 →
**0 次重建、0 次活动监视器建窗**；修复前一个实例里 24 条通知 → **16 次活动监视器建窗**。
通知本身仍然成串（13:09:1x 三条、13:10:5x 三条），只是不再有害。
一次拖拽要 1~2 秒，而旧版在 13:10:57~13:11:00 那种 3 秒内 4 条的连发里会把视图换掉 4 次
—— 这就是"完全拖不动"而不是"偶尔拖不动"的原因。

**这条解释不了"只有监视器拖不动"——已用计数证伪。** 今天 09:39 到修复版启动前那一段：106 条屏幕通知，
**卡片、弹药库、监视器各建窗 130 次**，三块完全一样；而用户说卡片和弹药库一直拖得动。
所以重建风暴会让**任何一块**的拖拽偶发被打断（值得修，也确实修了：修复后 44 条通知只建窗 1 次），
但它不是监视器专属的原因。**监视器专属的成因仍未找到**，而目前能生成的每一个假设
（`mouseDown` 到得了但 `mouseDragged` 不进、两套拖窗路径、tracking area、`setNeedsDisplay:` 重写…）
都只能用真鼠标区分：这台机器没有辅助功能权限，Computer Use 又绑不上 LSUIElement 的 DeskBoard。
下一步只能是用户亲手拖一次，看日志链路断在哪一环。

前面那几条嫌疑**都不是根因**，但结论留着有用：

**还有一条不依赖日志措辞的独立验证**：盯窗口号。修复前几乎每条通知都会换号（今天实录
45516 → 45586 → 45684 → 45792 → 46044 → 46905）；修复后取一个起点 46905，等 110 秒、期间又来
2 条通知，号**没变** —— 说明用户光标底下那个视图真的活着，这才是"拖得动"的前提。模态循环（合成事件抓不到，已证伪）、遮挡
（A/B 证伪）、调角模式 return（真 bug，但用户没进过那个模式）、tracking area 的
`NSTrackingEnabledDuringMouseDrag`（真不一致，但它解释不了"第一条 mouseDragged 都没日志"）。
`performWindowDragWithEvent:` 双路和"两路不互抢"守卫也留着 —— 少一种投递路径失败的可能。

## 环境要求

- macOS 13.0+
- Command Line Tools（`xcode-select --install`）
- clang

## 构建

```bash
./build.sh            # 构建 + 安装到 ~/Applications + 启动 + 桌面层窗口实测
./build.sh --build    # 只构建到 build/DeskBoard.app，不安装不启动
./build.sh --check    # 零警告编译 + 模型/布局断言（改完代码先跑这个）
./build.sh --dump     # 只对正在运行的实例做窗口层级校验
./build.sh --tools    # 只编译校验工具到 build/tools/
```

安装位置默认 `~/Applications`，可用 `INSTALL_DIR` 覆盖：

```bash
INSTALL_DIR=/Applications ./build.sh
```

### 关于 SDK 选择

本机默认 SDK 有时是坏的（`MacOSX27.0.sdk` 的 `.tbd` 含当前链接器不认的 `arm64e.x1-macos` 架构）。`build.sh` 里的 `pick_sdk` 不信 `xcrun` 默认值，逐个试候选 SDK，用一个最小链接测试挑第一个真能用的。

仓库里不放任何位图素材：图标由代码绘制，弹药库的底板则直接**采样用户自己桌面壁纸**里组件所在的那一块——所以换壁纸、挪位置，组件都天然融入，不会出现"在桌面上贴了一张桌面缩略图"的割裂感。采样失败时退回程序化渐变底。

## 菜单栏

菜单按**作用在哪个组件上**分层，不按功能分层。顶层是四块组件 + 全局项，**没有任何一项会同时移动两个组件**；唯一的全局动作是「锁定位置」，它只决定能不能拖，不改摆位。

| **卡片面板（系统状态）** | 组件 1 | 下面全是对这块板子的操作 |

| └ 恢复默认位置（右上） | 组件 1 | 把当前屏的卡片锚回右上 16/16；其他分辨率的档位不动 |

| 退出 DeskBoard | 全局 | `⌘Q` |

卡片 / 弹药库 / 活动监视器三块的窗口组、摆位档、四角位移、外观枚举、调角状态**完全独立**（`_windows` / `_places` / `_quad` / `_style` / `_editing` 对 `_vaultWindows` / `_vaultPlaces` / `_vaultQuad` / `_vaultStyle` / `_vaultEditing`），所以调角模式是三个独立开关：调弹药库不会把卡片窗口一起撑开，调活动监视器也不会动前两块。签到中心另有自己的 `_creditsWindows` / `_creditsPlaces` / `_creditsStyle`，只共用桌面图标层，没有调角。活动监视器的简略模式也单独存档（`MonitorCompact`），和它的外观 / 调角互不影响。调角态不存档，重启后三个开关都是关的。

## 弹药库

| 操作 | 结果 |
| --- | --- |
| 从桌面图标或任意访达窗口拖文件夹或常见文件进组件 | 搬进 `~/DeskBoard Vault/` 并登记 |
| 点卡片右上角的 ⇩ | 退回桌面，文件名还原。想放桌面用这个按钮，别用拖 |
| 双击卡片 | 在访达中打开 |
| 拖组件空白处 | 移动组件。**按在卡片上普通拖也是移动组件**，不会误触发拖出 |
| ⌥ + 拖卡片 | 拖到访达任意位置；落在空处就放回组件里，不会自作主张搬到桌面 |
| 扫桌面 | 桌面上的文件夹和合规矩的文件一次性入库（不合规的留在原地） |
| 开库 | 在访达里打开库目录 |
| 全退 | 库里所有文件夹退回桌面 |
| 收起 / 菜单栏「弹药库 ARMORY › 显示 / 隐藏」 | 整块隐藏，让出桌面图标 |
| 菜单栏「弹药库 ARMORY › 调角模式」 | **只**让弹药库进入调角，四个角各拖各的；配「复位角点」一起归零，卡片的调角态不受影响 |
| 菜单栏「弹药库 ARMORY › 透明度」 | 整块组件变透明，100% 起每 5% 一档一直到 5%，改的是窗口 alpha，四档外观和变形状态都跟着生效 |

**固定贴在桌面图标层**，和桌面图标同一层，所以它在所有应用窗口（全屏的也不例外）之下，物理上盖不到任何窗口。这条是硬约束：旧的「桌面置顶」开关会把窗口提到 `NSFloatingWindowLevel`、正好浮在应用窗口上面，已经连同菜单项和存档键一起删掉了。也不做"被遮挡就自动隐藏"——那种补丁会让组件在你松手几秒后凭空消失，比浮在窗口上面更难排查。

代价是访达桌面图标的拖放送不到这一层，所以从桌面往里拖东西请走「扫桌面」或「选文件/文件夹入库…」，两条路都一直可用。想省掉桌面图标中间那一跳，就直接把文件夹拖到组件上。

收不收由 `vault.m` 里一张**白名单**说了算，四个入口（拖放、选单、扫桌面、数据层）都走它：

- **收**：普通文件夹；后缀在表内的常见文件——视频、音频、图片、文档、压缩包、代码六类。
- **拒**：隐藏文件（`.DS_Store` 等）、符号链接、Finder 别名、`.app` / `.bundle` / `.framework` 这类「看着像文件、其实是目录」的包（搬走等于破坏应用）、没有后缀认不出格式的文件、以及不在表内的后缀。

是白名单不是黑名单：没在表里的后缀宁可拒掉也不冒险，以后想多收一种格式，往 `VaultExtKinds()` 里加一行即可。卡片上的图形和 meta 行按格式分——文件夹显示「N 项 · 体积」，文件显示「视频 · 体积」这类。撞名的会自动加序号（`素材 2`），退回时还原原名。

库目录是 `~/DeskBoard Vault/`，清单为同目录下的隐藏文件 `.vault.json`（另存一份 `.vault.json.bak`）。**刻意不放在 `Application Support/DeskBoard`**：2026-10-21 实测，腾讯柠檬清理废纸篓里的旧 DeskBoard 副本时，把 `Application Support/DeskBoard`、日志、偏好当成「卸载残留」整体抹掉，库文件和清单一起被永久删除（废纸篓、APFS 本地快照里都没有）。现在启动时若清单缺失而库目录里还有文件，会自动认领成条目；主清单读不出来则回退 `.bak`；认领/跳过多少条都会写进 `~/Library/Logs/DeskBoard.log`。


组件锁在桌面图标层，**在所有应用窗口之下**。所以卡片和弹药库只要你还开着一个窗口（终端、浏览器、这个工具本身），它们就点不动——事件全被上面的窗口吃掉。面板自己看不出来，它照样显示在那儿，于是就成了"看着好好的，点了没反应"。

因此弹药库被应用窗口盖住就临时让开（连续两次判定盖住才收，避免一掠而过时闪一下）；空出来了就回来，顺带把自己顶回本层最前——访达的桌面窗和组件是同一层，它一旦排到前面，面板也会看着正常却完全点不动。
