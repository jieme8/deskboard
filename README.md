# DeskBoard

macOS 桌面挂件。纯 Objective-C + AppKit，无第三方依赖，一条 `build.sh` 搞定编译、安装和实测校验。

桌面上常驻两块可拖拽的面板：

- **卡片面板** —— 油价、系统状态（CPU / GPU / 内存 / 磁盘 / 读写速率）和时段问候，支持多个屏幕可用区自动定位、拖角调宽高、四种外观。
- **弹药库 ARMORY** —— 桌面文件夹收纳架。把桌面上的文件夹拖进去，桌面立刻干净；卡架上显示每个文件夹的项数、体积和入库时间，支持双击打开、拖出退回、扫描桌面一键入库。卡片按格式画不同的图形（文件夹 / 视频 / 音频 / 图片 / 文档 / 压缩包 / 代码），四档外观可切换，透明度 100% 起每 5% 一档、一直到 5%。

两块面板各自记住自己在每块屏每个分辨率下的位置和四角形变，互不干扰。两块面板都固定贴在桌面图标层，任何模式下都不会浮到应用窗口上面（全屏窗口也不例外）——层级是硬约束，菜单里没有开关能改它。

弹药库的玻璃底板不是一张固定图片，而是每次从**用户真实的桌面壁纸**上采样组件背后那一块、模糊、提饱和后压一层暗角。和卡片面板共用同一套 `DeskBackdrop` 采样逻辑，所以换壁纸、挪位置都天然贴合。四档外观共用同一个 `DeskStyle` 枚举：实底卡采样壁纸，羽化暗角不采样只叠暗区，无底浮字和 HUD 贴窗完全透明、靠文字投影和青色描边撑可读性。

## 组件 3：活动监视器（CPU · 内存 · 能耗 · 网络）

四榜并列，每榜 4 个进程，全部读这台机器的真实数据，零权限、零弹窗。

- **口径**：CPU 走 `proc_pid_rusage` 的 user+system 时间两拍求差（rusage 给的是 mach 刻度，
  本机 1 刻度 = 41.667ns，忘了换算 %CPU 会少算 41.7 倍 —— `verify.m` 里"烧一核自报 99.9%"
  那条断言就是守这个）；内存是 `ri_resident_size`；能耗是**自算估算**（CPU 时间 + 唤醒次数加权，
  榜头标"能耗（估）"），原生活动监视器那个数走 IOReport，而这台系统的 IOKit 没导出 IOReport 符号；
  网络这一榜是**活跃 socket 数**，榜头才是系统总速率 —— 每进程字节数需要 nettop（实测烧 146% 单核）
  或未文档化的 NStat 管理器，都不适合常驻。
- **单位规则（这块板子被吐槽过两轮，规矩就三条）**：
  ① 榜头和榜内必须同一把尺 —— CPU 榜头原来印"整机 11%"而每行是"占一核 20.2%"，两个分母并排
  放着，人第一反应就是"总数怎么比单个进程还小"；现在榜头换算成全部核加起来的单核百分点
  （12 核满载 = 1200%），标题写"CPU 全核"，"总 ≥ 任意一行"由构造保证。
  ② 自造单位的绝对值不许上屏 —— 能耗每行原来印"191"，那是 `CPU% + 唤醒×0.08` 的裸分，
  没有任何人解读得出来；现在每行印**占全部进程能耗的比例**，榜头印"前4占 xx%"，
  两者共用同一个分母 `energyShareTotal`（同一次循环算出来的，不留第二套真相）。
  ③ 数字一律带单位 —— 每行 CPU 现在印 "20.2%"，不再是裸的 "20.2"。
  分母为 0 时印 "—" 或 "0%"，绝不印 `nan%`（`verify.m` 有专门一条守这个）。
- **"第二根线"这条的设计规矩**：每行底下一对 2pt 细条，上=现在、下=过去 12 小时平均，各自带一条整行宽的槽。
  用户撞上的"看不懂那根线"就是**只画了槽、槽里没有填充**的那种行（没有 12h 记录时）。所以规矩是：
  **槽不许空着**——没有记录就整根不画（`_cellCov > 0` 才画下面那根的槽），有记录时两根都装槽，
  这样任何一根线都能对应到它自己的填充上。槽在不同壁纸上的可见度差很多（Bare 档无底板，直接压在壁纸上），
  但这不是要修的东西：它只是量表的满刻度参照，永远和自己的填充一起出现。
  表头那句「亮条=现在 淡条=12小时平均」是这套元素的唯一说明处，改布局时别把它挤掉。
  **两根条子"同一把尺"现在有断言守着**（`verify.m`）：喂"12h 平均 == 当前值"要求两根一样长，
  喂"一半"要求淡条正好是亮条的一半。分母一旦被换成列内最大值或任何绝对尺，两条当场红
  （实测 0.500 vs 1.000、0.250 vs 0.500）。这条是淡条能对比的全部理由，之前一个断言都没有。
- **覆盖范围**：只列当前用户的进程（实测 542 可读 / 274 被拒，WindowServer 这类 root 进程读不到，
  `top` 能看到是因为它 setuid root）。所以顶栏明写"你的进程 N 个"。
- **每行那两根槽的代价量过**（2026-10-19）：离屏渲染工具 A/B 两次编译，只差"要不要画现在那根条的槽"，
  300 次整块重绘 0.202s vs 0.189s —— **一根槽 ≈ 0.04ms/次重绘**。重绘只在 5 秒一拍和悬停变化时发生，
  所以它不可能解释整机层面的 CPU 波动。以后有人怀疑"多画一根条子会不会变重"，先看这个数。
- **刷新 5 秒**，和原生活动监视器的默认档一致；动画表空闲即停，组件自己标脏才叫回来。
  实测整个 App 稳态 2.9% CPU（未变形）/ 0.2%（变形中）。
- **调角模式**：和卡片面板、弹药库同一条路 —— 先画正的烘成位图，再按四角投影。未变形时走
  实时绘制，所以文字是原生清晰度，只有拖角看形状时才付位图的清晰度代价。变形态整条悬停关掉
  （命中测试还在未变形坐标上，斜着放会点错行），窗影也关掉（外框是矩形，窗影会出卖它）。
  重烘只在换拍 / 改角 / 改外观 / 挪窗时发生，不跟缓动逐帧烘。

## 12 小时历史（活动监视器）

每行进程现在画**两根 2pt 条**：上面那根是这一拍的即时值，下面那根是过去 12 小时的平均值
（同一把尺，长短可直接比）。精确的 12h 数字在悬停浮层里。

为什么要自己攒：macOS 没有任何公开 API 能给"过去 12 小时"的任意指标 —— `getloadavg` 只到
15 分钟，`host_cpu_load_info` 和网卡计数都是"自开机累计"，而开机几天是常态，since-boot ≠ 12h。
所以 `DeskHistory` 把每 5 秒那一拍按分钟攒成桶，落盘在 `Application Support/DeskBoard/History-12h.plist`。

三个口径决定，都是实测后定的：

- **分母 = min(窗口, 窗口内真正攒到的秒数)**，不是写死的 43200。写死的话冷启动头一天分子只有
  几分钟、分母却是 12 小时，任何进程的 12h 条都是亚像素长度 —— 等于装好之后一整天看不到这个
  功能。用 min 之后攒满 12 小时自动收敛回字面口径，没攒满时是"已记录这段时间的平均"，界面拿
  `covered` 标"已记录 X 小时"，两个阶段都不撒谎（两条都有断言）。
- **只跟踪四榜前 6 的并集**（封顶 40 个 pid），不存全部 542 个进程。取前 6 而不是前 4 是给榜
  留滞后余量：一个进程从第 5 名掉出去时这一小时的平均还在，不会画着画着突然变 0。
- **只列当前活着的进程**，历史只作为它的一列。12h 榜上出现已经退出的进程会和"实时监视器"自相矛盾。
- **隐藏时继续采**：否则"隐藏 6 小时"会在历史里留 6 小时的洞，而分母按窗口算会把洞当成 0，
  恢复显示后数字长期偏低且看不出来。

两个实测教训：`leaders()` 一开始写成"四个指标各 sort 一遍 542 个进程"，整个 App 从 2.9% 顶到
**8.5% CPU**，改成一趟扫描 + 四个定长小数组才回到 3.4%；plist 读回来的桶是**不可变**容器，浅
`mutableCopy` 之后下一拍追加会撞 `-[__NSArrayI setObject:atIndexedSubscript:]`，而且只有"重启后
正好又采到同一 pid 的同一分钟"才炸 —— 表现为偶发 SIGABRT。

## 组件"点不动 / 拖不动"的排查顺序

**先查遮挡，再改代码** —— 三块组件都在 `kCGDesktopIconWindowLevel`（桌面图标层），
任何一个全屏窗口（远程桌面、投屏、某些截图/会议软件的覆盖层）压在它上面时，鼠标事件
根本送不到组件，这时候改拖拽代码是白改。一条命令就能分清：

```
./build/tools/probe_occlusion
```

它只把 **layer 0~1000 的普通窗口**算作遮挡（浏览器、IDE 这类真的吃点击的），
layer 极高的全屏覆盖层（远程桌面 / 投屏 / 会议软件）**单独归类、不算遮挡** —— 因为它真吃点击的话
用户整个桌面都点不动，把它算成遮挡会得出假结论（本机就有这么一个 layer≈INT32 的
`UURemoteServer` 全屏层，第一版把它误判成遮挡，把排查带偏了一整轮）。
同时报"被盖住百分之多少"和"四角 + 四边中点共 8 个抓取点还剩几个空着"，
因为只要有一个抓取点没被压住，用户就能拖。

**但这条命令只能在"拖不动"正在发生的那一刻作数。** 实测过一次：卡片面板和活动监视器同时被
普通窗口 100% 盖住、8 个抓取点全被压住 —— 可当时整屏那块区域亮度只有 29，而组件自身内容
平均 65，说明组件**连看都看不见**。看不见就意味着用户报"拖不动"那会儿肯定不是这个状态，
这条测量只能证明"现在挡着"，不能证明"当时是它挡的"。

所以正确的用法是：**拖不动的当场**跑一次 `probe_occlusion`，别事后跑。

**还有一类遮挡以前被漏掉：同层的 Finder 桌面图标窗。** 14:47:23 实测到一条
`layer=-2147483603 覆盖100% 访达` **排在活动监视器前面** —— 它和我们同一层，同层之间比排列顺序，
它在前头就会在覆盖区域把点击拿走。`probe_clickcatcher` 现在把"同层且在前"也算成吃点击。**注意：这条改动里"部分遮挡也报比例"那 3 行还没被真实场景跑到过**（构造过 23%/79% 两个矩形，
但桌面状态在两次命令之间就变了，没能复现）—— 别把它当成已验证的行为。

**但这条只见过一次，别把它当结论**：30 秒后再看就没有了；专门做实验确认**不是我的截图招出来的**
（截图前后同层列表都只有我们自己的两块窗）。一个来去匆匆的窗口只能造成**偶发**拖不动，
撑不起"完全拖不动"。它值得留着是因为 macOS 图标默认从右上角排、而监视器恰好贴右上，
所以两者重叠是有先天的 —— 怀疑撞上它时，用菜单「摆到 › 左下角」挪开再拖。

**先记住一件最朴素的事：这块组件按硬约束永远在你的应用窗口之下**（`kCGDesktopIconWindowLevel`，
不许盖住任何窗口）。所以只要有任何一个窗口压在它那块区域上，点上去到的就是那个窗口，
"拖不动"是必然的、不是 bug。13:59 实测：`MiniMax Code`（layer=0）**100%** 压住活动监视器、
`AI Worker`（layer=3）再压 58% —— 这个状态下它不可能被拖动。判"当时是不是这个原因"，
用 `probe_clickcatcher`（`全部` 或 `rect X Y W H`）在当场量一次即可。
顺手记一句：**桌面图标那条路已排除** —— 实测窗口列表里 Finder 根本没有与监视器同层、
或在它前面的窗口，所以"右上角图标列压住组件"这个想当然的说法不成立。

**一条命令自己看结论**（不用等 AI 读日志）：

```
python3 tools/diagnose_drag.py
```

它只取最近一次启动之后的日志，按 `按下 → 收到拖拽事件 → 拖动中 → 松手 位移` 这条链给判定：
没有按下 = 事件没进来；有按下没拖拽 = 断在投递层；有拖拽没松手 = 中途被打断；
链路完整但总位移≈0 = 被别处按存档重申回去了。三条分支都用合成日志验过，不是只会说"没数据"的摆设。
事后跑出来的遮挡，多半只是"你现在开着别的窗口"。

遮挡排掉之后，再验派发链：`./build/tools/probe_drag` 用
`[NSApplication postEvent:atStart:]` 把事件塞进本进程自己的队列（不碰系统事件流，
所以**不需要辅助功能权限**），跑一遍 run loop 让 AppKit 走完
NSApp → 窗口 → hitTest → 视图 的真实派发，看 `mouseDown/mouseDragged/mouseUp`
三段是不是都送到了视图。局限：`NSEvent.mouseLocation` 取的是真实光标，
"窗口到底位移了多少"测不了，只能测"事件到没到视图"。

**遮挡要用 A/B 判，不能只看"有没有被盖住"。** `probe_occlusion` 报 100% 被盖住，
只说明"此刻有一块窗口压在上面"，不说明"它吃点击"——`kCGWindowLevel` 里 Dock 有一块
layer=20 的全屏窗，任何桌面层组件都被它 100% 压着，但组件照样点得动（那块窗自己不吃鼠标）。
所以判遮挡必须拿**能拖的那块**当对照：

```
./build/tools/probe_clickcatcher 全部
```

它按 `CGWindowListCopyWindowInfo(OnScreenOnly)` 的**从前到后**顺序，对每块组件列出
压在它前面的窗口和各自覆盖率。实测三块组件被同一批窗口（Dock 全屏窗 + 一层
layer≈INT32 的远程桌面覆盖层）以完全相同的方式压着 —— 覆盖率相等就不是差别，
遮挡这条到此证伪，别再往下猜。

活动监视器这里**确实有一个模式陷阱**：`mouseDown:` 里原来写着
`if (_editing) { [self trackCornerDrag:event]; return; }`，一进调角模式整块组件一点都拖不动；
而卡片面板（`panel_view.m`）和弹药库（`vault_view.m`）在同一模式下是先
`DeskQuadHitTest`，**只有命中角点才 return**，没命中就照常拖窗。三块组件现在共用这一条规矩，
`verify.m` 里"开着调角模式按正中间，照样进入拖窗态"和"按在复位角点按钮上不拖窗"两条钉住它。

**时间线才是关键**：`git log -S nextEventMatchingMask -- monitor_view.m` 显示那个 8 秒模态循环
从 0.0.4（10-18 21:42）一直活到 0.0.11（10-19 09:49）才被删，而用户的抱怨是 11:11 提的、
描述的是**之前**的尝试 —— 极可能撞的就是那一版。在那一版里，非 key 的桌面层窗口在 `mouseDown:`
内自开 `nextEventMatchingMask:` 等拖拽事件，应用不活动时事件未必进得来，循环空等 8 秒后超时，
窗口一动不动。**注意别把两件事混了：我做过的是"我的测试抓不到旧写法"（证伪了测试），
从没证明"旧写法在真鼠标下无害"。** 现在两个真 bug 都已修掉（模态循环 09:49、重建风暴 13:44），
你抱怨时那版代码已经不存在了。

**但这条不是用户那一次"拖不动"的已证原因**：`~/Library/Logs/DeskBoard.log` 整份历史里只有
10-17 两条"卡片调角模式"，**没有任何一条活动监视器的调角开关** —— 用户根本没进过那个模式。
所以它是个真 bug（已修），不是他撞的那个。剩下两种可能靠一条日志分开：`mouseDown:` 最顶端
（任何提前 return 之前）打 `按下：调角=? 变形=? 双击=? 窗原点=?`。用户试一次之后，日志里
**有**这行 = 事件送到了视图，问题在算法；**没有** = 事件根本没到，问题在层序或某个吃点击的
窗口 —— 那时候用菜单里的「摆到（不用按住拖）」换角落，不依赖按住组件也能搬。

日志还给出两条硬事实：**双击过监视器**（`10:55 活动监视器 打开活动监视器看 pid 809`，那行只在
`mouseDown:` 的双击分支里）—— 所以事件到得了视图，遮挡/层级一类解释全部出局；**弹药库真拖过 71 次**
（「拖动中 光标… 窗口原点…」逐帧对得上）—— 所以同一套 `VaultDragFrame` + 桌面层窗口在真鼠标下是有效的。
顺着这条把最后一处不对称对齐了：**只有监视器用 `setFrame:display:animate:NO` 挪窗**，卡片用
`setFrameOrigin:`、弹药库用 `setFrame:display:`。但**这条不是已证根因**：负向对照量过，换回
`animate:` 那版 216 条断言一条不动 —— 校验 CLI 里没有真窗口服务器事务，这个差异只有真鼠标能判。
所以监视器也补上了弹药库同款 trace（每 8 帧记「拖动中 光标+窗口原点」、松手记总位移），
一次尝试就能看出断在哪一环。

**已找到并修掉一个真 bug（但它不是"只有监视器拖不动"的原因，见本节末尾）**：`screenDidChange:` 每次都把三块组件的窗口全部销毁重建。
这台机器的显示配置每 8~30 秒抖一次（日志实测 12:43:18/:32/:39/:47/:57、12:46:31/:56 连续多条
「屏幕参数变更，按存档重申位置」，**每条后面都紧跟三行建窗**）。旧写法对每条通知都无条件
`rebuildWindows` + `rebuildVaultWindows` + `rebuildMonitorWindows` —— 用户按住活动监视器拖到
一半，那个视图就被换成新的，`mouseDragged:` 永远送不到。这正好对上前面两条证据：`mouseDown`
到得了（10:55 双击那条），而整份历史没有一条「收到拖拽事件」。附带症状也解释了：活动监视器
每次重建后空板几秒（榜要等下一拍才有数据）。
修法是先比**屏幕配置指纹**（屏数 + 每屏 `displayID`/点尺寸/原点）：真的变了才重建，否则只重申位置。
**实机验证**：新版 12:48:46 又收到一条通知，日志写「配置指纹没变，只重申位置，不重建窗口」，
后面不再跟建窗行。

**现场统计（同一份日志，按启动分段数出来）**：修复后那次启动至今 15 条屏幕通知 →
**0 次重建、0 次活动监视器建窗**；修复前一个实例里 24 条通知 → **16 次活动监视器建窗**。
通知本身仍然成串（13:09:1x 三条、13:10:5x 三条），只是不再有害。
一次拖拽要 1~2 秒，而旧版在 13:10:57~13:11:00 那种 3 秒内 4 条的连发里会把视图换掉 4 次
—— 这就是"完全拖不动"而不是"偶尔拖不动"的原因。

**这条解释不了"只有监视器拖不动"——已用计数证伪。** 今天 09:39 到修复版启动前那一段：106 条屏幕通知，
**卡片、弹药库、监视器各建窗 130 次**，三块完全一样；而用户说卡片和弹药库一直拖得动。
所以重建风暴会让**任何一块**的拖拽偶发被打断（值得修，也确实修了：修复后 44 条通知只建窗 1 次），
但它不是监视器专属的原因。**监视器专属的成因仍未找到**，而目前能生成的每一个假设
（`mouseDown` 到得了但 `mouseDragged` 不进、两套拖窗路径、tracking area、`setNeedsDisplay:` 重写…）
都只能用真鼠标区分：这台机器没有辅助功能权限，Computer Use 又绑不上 LSUIElement 的 DeskBoard。
下一步只能是用户亲手拖一次，看日志链路断在哪一环。

前面那几条嫌疑**都不是根因**，但结论留着有用：

**还有一条不依赖日志措辞的独立验证**：盯窗口号。修复前几乎每条通知都会换号（今天实录
45516 → 45586 → 45684 → 45792 → 46044 → 46905）；修复后取一个起点 46905，等 110 秒、期间又来
2 条通知，号**没变** —— 说明用户光标底下那个视图真的活着，这才是"拖得动"的前提。模态循环（合成事件抓不到，已证伪）、遮挡
（A/B 证伪）、调角模式 return（真 bug，但用户没进过那个模式）、tracking area 的
`NSTrackingEnabledDuringMouseDrag`（真不一致，但它解释不了"第一条 mouseDragged 都没日志"）。
`performWindowDragWithEvent:` 双路和"两路不互抢"守卫也留着 —— 少一种投递路径失败的可能。

## 构建

```bash
./build.sh            # 构建 + 安装到 ~/Applications + 启动 + 桌面层窗口实测
./build.sh --build    # 只构建到 build/DeskBoard.app，不安装不启动
./build.sh --check    # 零警告编译 + 模型/布局断言（改完代码先跑这个）
./build.sh --dump     # 只对正在运行的实例做窗口层级校验
./build.sh --tools    # 只编译校验工具到 build/tools/
```

安装位置默认 `~/Applications`，可用 `INSTALL_DIR` 覆盖：

```bash
INSTALL_DIR=/Applications ./build.sh
```

### 关于 SDK 选择

本机默认 SDK 有时是坏的（`MacOSX27.0.sdk` 的 `.tbd` 含当前链接器不认的 `arm64e.x1-macos` 架构）。`build.sh` 里的 `pick_sdk` 不信 `xcrun` 默认值，逐个试候选 SDK，用一个最小链接测试挑第一个真能用的。

| `vault.h` / `vault.m` | 弹药库数据层：清单、搬文件、异步统计目录体积 |
| `vault_art.h` / `vault_art.m` | 弹药库美术层：底图模糊压暗、扫描线、准星、文件夹图形 |
| `vault_view.h` / `vault_view.m` | 弹药库组件：卡架布局、拖放、动画、操作坞 |

| `mock/` | 测试用假数据 |

图标由 `tools/mkicon.m` 在代码里绘制，`build.sh` 负责铺满 10 个尺寸并打成 `.icns`，所以仓库里不放二进制素材，改一笔图标就能重新出全套。

仓库里不放任何位图素材：图标由代码绘制，弹药库的底板则直接**采样用户自己桌面壁纸**里组件所在的那一块——所以换壁纸、挪位置，组件都天然融入，不会出现"在桌面上贴了一张桌面缩略图"的割裂感。采样失败时退回程序化渐变底。

## 菜单栏

菜单按**作用在哪个组件上**分层，不按功能分层。顶层只有两块面板 + 全局项，**没有任何一项会同时动到两个组件**。

| 菜单项 | 作用对象 | 说明 |
| --- | --- | --- |
| **卡片面板（油价 · 系统状态 · 问候）** | 组件 1 | 下面全是对这块板子的操作 |
| └ 显示 / 隐藏 | 组件 1 | 带勾，隐藏时菜单栏图标变灰 |
| └ 外观 ▸ | 组件 1 | 四选一，只改卡片这套（存档键 `Style`） |
| └ 保存当前位置（拖完再点） | 组件 1 | 只对卡片有用——卡片拖动先进"待保存"，弹药库拖完直接落档 |
| └ 调角模式 | 组件 1 | 带勾，只让卡片进入调角 |
| └ 复位角点 | 组件 1 | 只清 `_quad` |
| **弹药库 ARMORY（文件夹收纳）** | 组件 2 | 下面全是对弹药库的操作 |
| └ 显示 / 隐藏 | 组件 2 | 带勾，组件唯一开关；被应用窗口盖住不归它管，层级本来就压在下面 |
| └ 外观 ▸ | 组件 2 | 同样四选一，和卡片各存各的档（`VaultStyle`） |
| └ 透明度 ▸ | 组件 2 | 每 5% 一档，100%→5% 共 20 档，落在窗口 alpha 上（`VaultAlpha`） |
| └ 选文件/文件夹入库… | 组件 2 | 绕开拖放的入库入口，开访达多选；收不收由白名单判 |
| └ 调角模式 | 组件 2 | 带勾，只让弹药库进入调角 |
| └ 复位角点 | 组件 2 | 只清 `_vaultQuad` |
| **活动监视器 ACTIVITY（CPU · 内存 · 能耗 · 网络）** | 组件 3 | 下面全是对这块板子的操作 |
| └ 显示 / 隐藏 | 组件 3 | 带勾（`MonitorHidden`） |
| └ 外观 ▸ | 组件 3 | 同样四选一，各存各的档（`MonitorStyle`） |
| └ 调角模式 | 组件 3 | 带勾，只让活动监视器进入调角 |
| └ 复位角点 | 组件 3 | 只清 `_monitorQuad` |
| └ 打开原生活动监视器 | 组件 3 | 双击某一行是同一个入口 |
| 打开数据目录… | 全局 | 同一个数据目录，两个组件的档案都在里面 |
| 退出 DeskBoard | 全局 | `⌘Q` |

三块组件的窗口组、摆位档、四角位移、外观枚举、调角状态**完全独立**（`_windows` / `_places` / `_quad` / `_style` / `_editing` 对 `_vaultWindows` / `_vaultPlaces` / `_vaultQuad` / `_vaultStyle` / `_vaultEditing`），所以调角模式是三个独立开关：调弹药库不会把卡片窗口一起撑开，调活动监视器也不会动前两块。调角态不存档，重启后三个开关都是关的。

## 弹药库

| 操作 | 结果 |
| --- | --- |
| 从桌面图标或任意访达窗口拖文件夹或常见文件进组件 | 搬进 `~/Library/Application Support/DeskBoard/Vault/` 并登记 |
| 点卡片右上角的 ⇩ | 退回桌面，文件名还原。想放桌面用这个按钮，别用拖 |
| 双击卡片 | 在访达中打开 |
| 拖组件空白处 | 移动组件。**按在卡片上普通拖也是移动组件**，不会误触发拖出 |
| ⌥ + 拖卡片 | 拖到访达任意位置；落在空处就放回组件里，不会自作主张搬到桌面 |
| 扫桌面 | 桌面上的文件夹和合规矩的文件一次性入库（不合规的留在原地） |
| 开库 | 在访达里打开库目录 |
| 全退 | 库里所有文件夹退回桌面 |
| 收起 / 菜单栏「弹药库 ARMORY › 显示 / 隐藏」 | 整块隐藏，让出桌面图标 |
| 菜单栏「弹药库 ARMORY › 调角模式」 | **只**让弹药库进入调角，四个角各拖各的；配「复位角点」一起归零，卡片的调角态不受影响 |
| 菜单栏「弹药库 ARMORY › 透明度」 | 整块组件变透明，100% 起每 5% 一档一直到 5%，改的是窗口 alpha，四档外观和变形状态都跟着生效 |

**固定贴在桌面图标层**，和桌面图标同一层，所以它在所有应用窗口（全屏的也不例外）之下，物理上盖不到任何窗口。这条是硬约束：旧的「桌面置顶」开关会把窗口提到 `NSFloatingWindowLevel`、正好浮在应用窗口上面，已经连同菜单项和存档键一起删掉了。也不做"被遮挡就自动隐藏"——那种补丁会让组件在你松手几秒后凭空消失，比浮在窗口上面更难排查。

代价是访达桌面图标的拖放送不到这一层，所以从桌面往里拖东西请走「扫桌面」或「选文件/文件夹入库…」，两条路都一直可用。想省掉桌面图标中间那一跳，就直接把文件夹拖到组件上。

收不收由 `vault.m` 里一张**白名单**说了算，四个入口（拖放、选单、扫桌面、数据层）都走它：

- **收**：普通文件夹；后缀在表内的常见文件——视频、音频、图片、文档、压缩包、代码六类。
- **拒**：隐藏文件（`.DS_Store` 等）、符号链接、Finder 别名、`.app` / `.bundle` / `.framework` 这类「看着像文件、其实是目录」的包（搬走等于破坏应用）、没有后缀认不出格式的文件、以及不在表内的后缀。

是白名单不是黑名单：没在表里的后缀宁可拒掉也不冒险，以后想多收一种格式，往 `VaultExtKinds()` 里加一行即可。卡片上的图形和 meta 行按格式分——文件夹显示「N 项 · 体积」，文件显示「视频 · 体积」这类。撞名的会自动加序号（`素材 2`），退回时还原原名。


组件锁在桌面图标层，**在所有应用窗口之下**。所以卡片和弹药库只要你还开着一个窗口（终端、浏览器、这个工具本身），它们就点不动——事件全被上面的窗口吃掉。面板自己看不出来，它照样显示在那儿，于是就成了"看着好好的，点了没反应"。

因此弹药库被应用窗口盖住就临时让开（连续两次判定盖住才收，避免一掠而过时闪一下）；空出来了就回来，顺带把自己顶回本层最前——访达的桌面窗和组件是同一层，它一旦排到前面，面板也会看着正常却完全点不动。
